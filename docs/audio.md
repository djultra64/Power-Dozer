# Prototype audio

Current status (2026-10-10): stereo mixing, RSP yielding and recovery
with simulated SDL failures have tests. Two isolated six-minute sessions
kept audio active during movement, pause and restart. This still
does not demonstrate total stability: both an audio stop
with graphics active and a joint stall during startup were observed. The beta
remains under investigation; earlier data is preserved as historical
evidence with its original scope.

Direct runtime initialization omitted `set_message_queue_control`, which
its normal startup applies before `preinit`. Standard settings are now
applied to retry SP/DP/Timer/SI when a queue is full. A test
with actual SDK code demonstrated event loss before the adjustment and
subsequent delivery exactly once. The long regression passed, but a startup
stall reappeared; that failure is not attributed to a cause that has not yet been proven.

`BC_TRACE_AUDIO_STATE=1` logs bounded states of the original frame and reply
queues when scheduler messages are received. The private tester
provides `--capture-hang`: it collects native stacks and queues when it detects
stopped counters or a transition exceeding its timeout. Diagnostic files
are stored in `.local/qa`, and a capture never turns a failure into acceptance.

Yielding the RSP to audio allows PCM production to continue while
RT64 consumes a slow graphics list. The earlier run stopped after
9–12 audio tasks. After the fix, the following was verified:

| Test | Duration | Audio tasks | Result |
|---|---:|---:|---|
| Isolated display, scale 1, SDL dummy | 90 s | 2,699 | Progress during intros, title and demo; normal exit. |
| 4K, 16:9, requested target 120, SDL dummy | 35 s | 1,049 | Audio keeps advancing under heavy graphics load. |
| Desktop window, scale 3, PipeWire/PulseAudio | 25 s | 748 | 747 buffers accepted, none rejected; normal exit. |

The captured mix is 16-bit stereo PCM at 22,050 Hz. The executable
was confirmed to have an active stream directed to the local output device.
The 25-second capture contains 548,608 frames (24.88 seconds of PCM),
including silence generated by the game. Channels contain different data
in 95.1% of frames. This data establishes sound production and delivery;
it does not replace an auditory comparison with the original game.

## Cause and fix

The earlier graphics adaptation reported SP completion after reading the
list to prevent the game from reusing it while RT64 was reading.
However, `osSpTaskYield` still did nothing. The original scheduler
waited for that yield to start audio. A slow list accumulated several
timed audio frame notifications; afterward, the audio thread could generate
a task and wait for a reply without a request having been made to start it.

The host now recognizes a yield with SP state `0x181` and its interrupt.
RT64 retains the list and can finish reading it while the audio RSP
works on another thread. Graphics completion remains pending if the task is
suspended. On resume, it waits for the read or reports completion
already obtained, without processing the list a second time. Graphics memory is not
released early. Normal completion state returns to `0x201`.

The two samples of each stereo frame are also swapped: word-swapped
N64 RAM contains `[R,L]` for the host, while
SDL expects `[L,R]`. A test uses isolated channel impulses and signed
values to verify the order without relying on mono music or listening.

The AI queue still accepts two buffers and reports the active buffer's
remaining bytes. Controller Pak CRCs remain original recompiled CPU code:
they are not hardware operations. This fix removes the CRC diagnostic
exit encountered when returning to the frontend during one of the tests.

## Repeat the tests

```bash
ctest --test-dir build --output-on-failure
python3 -m unittest discover -s tests -v
./'Run Blast Corps.sh' --seconds 90 --scale 1 \
  --capture-audio .local/evidence/audio-test.wav \
  > .local/evidence/audio-test.log 2>&1
python3 tools/check_audio_probe.py .local/evidence/audio-test.log
```

The checker requires at least 20 seconds of logging, VI and audio task
counters advancing between reports, probe completion, a
non-silent PCM signal and no fatal events. Three Python tests check
that a joint VI/audio freeze and an incomplete run are rejected,
and that a final report matching the last periodic snapshot is accepted.
Its failure against `run-sp-order.log` reproduces the earlier symptom. It passed against
`audio-long.log`, `audio-4k.log` and `audio-desktop.log`. Logs and WAV files
remain in `.local/evidence/`, outside Git. `BC_TRACE_AUDIO=1` enables
detailed logging of scheduler and sound-thread messages.

## Evidence limitations

An observation of an empty SDL queue does not by itself prove an audible dropout:
the backend may have samples already transferred to its buffer. One was observed
in the actual output test; dummy tests record many more. No claim is made
of a total absence of clicks or underruns. The capture saves buffers submitted
before the backend, so it does not record silence inserted by the driver.

The actual output capture has 44 saturated samples out of 1,097,216 (0.004%).
The original amplitude is not changed and no limiter is added; a reference is needed
to determine whether that saturation belongs to the original mix.

Perceptual comparison, audio from all missions, broader transition
coverage and recovery with the physical device remain pending.
Pause/restart and simulated output failures have native tests;
the intermittent hangs described at the beginning remain pending. Complete
playability also requires additional coverage.
